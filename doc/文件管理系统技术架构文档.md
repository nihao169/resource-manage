# 文件管理系统技术架构文档

版本：1.1  
状态：架构基线  
适用范围：首期单机部署及后续同构扩容

## 文档目的

本文档定义文件管理系统的技术架构、组件边界、核心数据模型、接口分组和运行要求。系统面向文件上传、目录管理、版本管理、权限控制、元数据搜索、下载、回收站、审计和备份等场景，重点保证文件原件与业务元数据之间的边界清晰，并使关键写操作可校验、可重试和可恢复。

本文档是实现、测试和部署的共同基线。未在本文档中定义的扩展能力不得绕过既有权限、审计、事务和存储边界。

配套开发契约：[PostgreSQL表结构设计](PostgreSQL表结构设计.md)、[MinIO对象规则](MinIO对象规则.md)、[前后端接口定义](前后端接口定义.md)。具体字段、对象键、请求响应和MVP标记以这三份同版本契约为准。

## 架构结论

系统由 Vue、Nginx、FastAPI、PostgreSQL 和 MinIO 组成。

- Vue 提供单页应用和用户交互。
- Nginx 提供 HTTPS、静态资源、反向代理和入口级基础限流。
- FastAPI 是唯一业务后端，负责认证、鉴权、业务规则、事务协调和对象访问。
- PostgreSQL 是用户、权限、目录、文件、版本、上传、会话、审计和运维记录的权威来源。
- MinIO 是临时上传对象、不可变文件内容、历史版本内容和备份包的权威来源。

所有上传内容统一作为文件处理。系统不提取或保存正文，不生成文本分块，也不依据文件内容提供搜索能力。搜索只使用文件及其关联实体的元数据。

## 已确认的架构决策

| 决策项 | 选择 | 说明 |
| --- | --- | --- |
| Web 前端 | Vue 单页应用 | 构建后由 Nginx 提供静态资源 |
| 后端 | FastAPI | 唯一业务入口，所有存储访问均由后端发起 |
| 业务数据库 | PostgreSQL | 保存全部业务元数据、权限、会话和审计数据 |
| 对象存储 | MinIO | 保存临时上传对象和不可变文件内容 |
| 文件模型 | 统一文件模型 | 不区分文档与普通文件 |
| 搜索范围 | 元数据搜索 | 不读取文件内容，只搜索受控元数据字段 |
| 后台任务 | 不设置 | 首期不引入常驻 Worker、Scheduler 或任务队列 |
| 一致性方式 | 本地事务加幂等补偿 | 不使用分布式事务 |
| 下载方式 | 后端鉴权后流式转发 | 浏览器不直接获得对象存储访问凭据 |
| 部署方式 | Docker Compose 单机部署 | 各服务使用固定版本镜像和独立数据卷 |
| 监控 | 可选启用 | Prometheus 和 Grafana 不进入核心业务链路 |

## 架构范围

系统首期包括：

- 管理员和使用者两级角色。
- 用户登录、刷新会话、退出、冻结和强制下线。
- 空间、目录、标签和自定义元数据管理。
- 单文件上传、批量选择、分片上传、断点续传和服务端校验后的内容去重；不提供秒传。
- 文件元数据编辑、移动、复制、软删除、恢复和彻底清理。
- 不可变版本、历史版本查看、下载和恢复为新版本。
- 基于文件名、描述、目录、标签、MIME、上传者、自定义元数据和时间的搜索。
- 配额、审计、健康检查、备份恢复和一致性检查。

系统首期不包括：

- 文件正文提取、正文预览或正文搜索。
- 文件内容差异比较。
- 在线协作编辑、内容审核和工作流审批。
- 常驻异步任务、定时任务服务和消息队列。
- 批量移动、批量删除、批量打标签等高风险管理操作。
- 浏览器直连对象存储下载。

## 架构原则

1. PostgreSQL 是业务状态和权限判断的唯一权威来源。
2. MinIO 只保存对象内容，不保存业务权限或文件归属判断。
3. 文件内容写入成功与业务版本提交必须通过固定顺序和补偿逻辑衔接。
4. 文件版本不可变；恢复历史版本时创建新版本。
5. 所有受保护请求都在后端重新鉴权，前端隐藏按钮不构成授权。
6. 所有修改操作必须具备幂等边界或唯一约束。
7. 上传和下载全程使用流式处理，不把完整文件加载到 API 进程内存。
8. 删除采用先软删除、后受控物理清理的两阶段方式。
9. 搜索只能读取元数据，不能打开或解析 MinIO 中的文件内容。
10. 核心功能只依赖 PostgreSQL 与 MinIO 的可用性。

## 业务逻辑定义

### 文件统一模型

所有允许上传的内容均创建统一的逻辑文件和不可变版本。不根据 MIME、扩展名或内容建立不同的数据处理链路。

| 上传内容 | MinIO | PostgreSQL | 可搜索内容 |
| --- | --- | --- | --- |
| PDF、Word、文本和代码文件 | 保存不可变原件 | 保存文件、版本、MIME、大小、哈希和业务元数据 | 仅元数据 |
| 图片、音频和视频 | 保存不可变原件 | 保存文件、版本、MIME、大小、哈希和业务元数据 | 仅元数据 |
| 压缩包和其他允许的二进制文件 | 保存不可变原件 | 保存文件、版本、MIME、大小、哈希和业务元数据 | 仅元数据 |
| 禁止类型、超限或超配额文件 | 不形成正式对象 | 只保留必要的失败状态和审计 | 不可搜索 |

MIME 与扩展名用于上传策略、格式展示、筛选和安全响应头，不改变文件的数据模型。

### 上传整体流程

```text
选择一个或多个文件
        |
        v
前端为每个文件创建独立上传会话
        |
        v
后端校验账号、空间、目录、声明大小、允许类型和配额
        |
        v
前端按分片上传，后端记录每个已确认分片
        |
        v
完成上传：合并临时对象并重新计算实际大小和 SHA-256
        |
        +-- 校验失败 --> 标记上传失败，保留可审计结果
        |
        v
在 PostgreSQL 事务中提交逻辑文件、V1 版本和对象引用
        |
        v
返回文件与版本结果
```

一次批量选择只负责汇总展示。每个文件都是独立上传事务，一个文件失败不得回滚其他文件。

### 查询、读取和下载流程

- 文件列表先验证账号状态和空间成员关系，再应用目录、标签、格式、上传者、日期和状态筛选。
- 搜索在相同权限边界内匹配元数据，并只返回当前有权访问的文件。
- 查看文件详情时从 PostgreSQL 获取逻辑文件、当前版本、历史版本、标签和自定义元数据。
- 下载当前或历史版本时，FastAPI 先鉴权并校验版本状态，再从 MinIO 流式读取对象。
- 下载响应返回文件名、MIME、大小、版本号和 SHA-256，并使用安全的 `Content-Disposition`。

### 文件管理流程

- 使用者只能修改、移动、复制、发布版本、删除或恢复自己拥有的文件。
- 管理员可以管理全部文件，但管理员代为发布版本不会改变文件所有者。
- 修改文件名、描述、目录、标签和自定义元数据不修改历史版本内容。
- 复制文件会创建新的逻辑文件和 V1 版本，并复用不可变内容对象。
- 恢复历史版本会创建一个引用历史内容对象的新版本。
- 软删除后文件只在回收站可见；物理清理必须经过管理员二次确认。

### 管理员流程

- 管理用户状态、角色、强制下线和密码重置。
- 管理空间、配额、允许类型、上传并发和密码策略。
- 查询审计事件、备份记录、健康状态和一致性检查结果。
- 逐项恢复或彻底清理回收站文件。
- 执行受控备份、恢复演练和对象引用核对。

## 三种结构及其关系

系统同时维护三种互相关联但职责不同的结构：

1. 逻辑目录结构：由 `directories` 和 `files` 表定义，用于用户浏览和权限过滤。
2. 不可变版本结构：由 `file_versions` 定义，一个逻辑文件拥有顺序递增的版本链。
3. 物理对象结构：由 `content_objects` 映射到 MinIO 对象，允许多个版本安全引用相同内容。

```text
空间
  `-- 目录
       `-- 逻辑文件
            |-- V1 --+
            |-- V2 --+--> 内容对象 --> MinIO object_key
            `-- V3 ------> 另一内容对象 --> MinIO object_key
```

目录移动只改变逻辑位置；发布版本只追加版本记录；内容去重只影响物理对象引用，不合并逻辑文件、所有权或权限。

## 容器架构

```text
+----------------------------------------------------------------------------------+
|                                  单机宿主机                                      |
|                                                                                  |
|  Internet --> Nginx --> Vue 静态资源                                             |
|                    `--> FastAPI                                                  |
|                           |                                                      |
|                           +--> PostgreSQL：业务元数据、会话、审计                |
|                           `--> MinIO：临时对象、不可变文件、备份包               |
|                                                                                  |
|  可选：Prometheus、Grafana                                                       |
+----------------------------------------------------------------------------------+
```

FastAPI 是唯一业务后端。PostgreSQL 与 MinIO 不相互主动调用，所有业务访问均由 FastAPI 发起。

### 容器清单

| 服务 | 建议实现 | 主要职责 | 公网端口 | 持久化 |
| --- | --- | --- | --- | --- |
| nginx | Nginx stable 与 Vue 构建产物 | HTTPS、静态页面、反向代理和基础限流 | 80、443 | 证书和访问日志 |
| api | Python 3.12 与 FastAPI | 全部同步业务 API | 无 | 临时流式缓冲目录 |
| postgres | PostgreSQL | 全部业务元数据、会话和审计 | 无 | 独立数据卷 |
| minio | MinIO | 临时上传对象、不可变内容和备份包 | 无 | 独立数据卷 |

Prometheus 和 Grafana 可通过 Compose profile 启用。备份由受控的一次性 Compose 命令或宿主机定时命令执行，不运行常驻调度容器。

### 网络与端口

| 网络 | 加入服务 | 规则 |
| --- | --- | --- |
| edge | nginx | 唯一接收公网流量的网络 |
| app | nginx、api | Web 与 API 通信网络 |
| data | api、postgres、minio | 数据网络，不映射公网端口 |

宿主机只开放 80、443 和受限来源 SSH。PostgreSQL 5432、MinIO 9000 和 MinIO Console 9001 不得映射到公网地址。

## 前端逻辑架构

前端采用 Vue 单页应用，负责页面路由、文件列表、组合筛选、上传队列和操作反馈。文件归属、访问权限和最终状态都由后端决定。

### 主要模块

| 模块 | 主要职责 |
| --- | --- |
| 登录与会话 | 登录、刷新、退出和失效跳转 |
| 文件浏览 | 全部文件、我的上传、目录、回收站和详情 |
| 搜索与筛选 | 元数据关键词、目录、格式、标签、上传者、日期和状态 |
| 上传中心 | 批量选择、独立进度、断点续传和失败重试 |
| 版本管理 | 版本列表、版本下载、发布版本和恢复历史版本 |
| 文件操作 | 修改元数据、移动、复制、标签、删除和恢复 |
| 管理中心 | 用户、空间、配置、审计、备份和组件状态 |

### 文件列表展示

文件列表统一展示：

- 文件名、扩展名和 MIME。
- 所在空间与目录。
- 文件所有者与当前版本上传者。
- 当前版本号、大小、更新时间和 SHA-256 摘要。
- 标签、自定义元数据和文件状态。

筛选状态编码到 URL 查询参数，刷新、返回和复制链接时保持一致。列表使用分页或虚拟化渲染。

### 操作边界

| 功能 | 使用者 | 管理员 |
| --- | --- | --- |
| 文件浏览与搜索 | 查看所属空间内有权访问的文件 | 查看全部或选定空间文件 |
| 我的上传 | 查看本人拥有的逻辑文件 | 可按任意所有者筛选 |
| 文件管理 | 只管理本人文件 | 管理全部文件 |
| 回收站 | 恢复本人文件 | 恢复或彻底清理任意文件 |
| 系统管理 | 不显示 | 用户、配置、审计、备份和状态 |

前端操作可见性只改善使用体验。直接构造请求或替换资源编号时，后端仍必须重新鉴权。

## 数据组件职责

| 组件 | 保存内容 | 权威级别 | 丢失后的处理 |
| --- | --- | --- | --- |
| PostgreSQL | 用户、权限、空间、目录、文件、版本、标签、自定义元数据、上传、会话、审计和备份记录 | 业务权威来源 | 从数据库备份恢复 |
| MinIO | 临时上传对象、不可变内容对象和备份包 | 文件内容权威来源 | 从对象备份恢复并校验哈希 |

### PostgreSQL 核心模型

| 表 | 关键字段 | 主要约束 |
| --- | --- | --- |
| users | id、username、password_hash、role、status、token_version、password_changed_at | username 唯一；role 为 admin 或 user |
| refresh_sessions | id、user_id、token_hash、token_id、expires_at、revoked_at、last_used_at | 只保存令牌哈希；token_id 唯一 |
| spaces | id、name、quota_bytes、used_bytes、status | 有效名称唯一；used_bytes 按逻辑版本大小计费 |
| space_members | space_id、user_id、status、created_at | `(space_id, user_id)` 唯一 |
| directories | id、space_id、parent_id、name、path_key | 禁止形成目录循环；同级有效名称唯一 |
| files | id、space_id、directory_id、owner_id、name、description、current_version_id、status、deleted_at、deleted_by、created_at、updated_at | 逻辑文件与物理对象解耦 |
| content_objects | id、bucket、object_key、size、sha256、reference_count、status、created_at | `(sha256, size)` 唯一；引用数不得小于零 |
| file_versions | id、file_id、version_no、version_note、content_object_id、size、sha256、mime、retained_until、legal_hold、restored_from_version_id、created_by、created_at | `(file_id, version_no)` 唯一；版本不可变 |
| tags | id、space_id、name、status | 同一空间内有效名称唯一 |
| file_tags | file_id、tag_id、created_by、created_at | 联合主键 |
| metadata_fields | id、space_id、name、value_type、required、status | 同一空间内有效名称唯一；类型使用受控枚举 |
| file_metadata_values | file_id、field_id、value_text、value_number、value_date、value_boolean | `(file_id, field_id)` 唯一；只写匹配类型的值列 |
| upload_batches | id、user_id、total_count、completed_count、failed_count、created_at | 只汇总批量选择结果 |
| uploads | id、batch_id、user_id、target_file_id、original_name、expected_size、actual_size、expected_sha256、actual_sha256、mime、minio_upload_id、temp_object_key、status、expires_at、idempotency_key | 幂等键在用户范围唯一 |
| upload_parts | id、upload_id、part_no、size、etag、checksum、status、confirmed_at | `(upload_id, part_no)` 唯一 |
| cleanup_attempts | id、file_id、requested_by、confirmation_id、status、failure_detail、started_at、finished_at | 每次只处理一个逻辑文件 |
| system_settings | key、value、value_type、updated_by、updated_at | key 唯一；只允许受控配置项 |
| audit_events | id、actor_id、action、target_type、target_id、request_id、result、detail、created_at | 只追加，不允许修改历史记录 |
| backup_runs | id、scope、started_at、finished_at、status、checksum、remote_key | 保存每次备份结果 |

`file_versions.content_object_id` 是版本到物理内容的唯一引用。版本表冗余保存大小和哈希，用于历史展示与下载校验。物理删除必须同时检查引用计数和实际版本引用。

空间配额按全部现存逻辑版本大小计算，包括回收站版本；只有物理清理才释放配额。内容去重不降低配额占用。创建上传会话和最终提交时都必须检查配额。

### 权限判定矩阵

| 操作 | 使用者 | 管理员 |
| --- | --- | --- |
| 查看、搜索、下载当前或历史版本 | 账号有效且属于文件所在空间 | 可访问全部有效文件 |
| 修改元数据、移动、复制、标签、发布或恢复版本 | 仅文件所有者 | 可操作全部文件 |
| 软删除、从回收站恢复 | 仅文件所有者 | 可操作全部文件 |
| 彻底清理、用户管理、配置、审计和备份 | 禁止 | 二次确认后允许 |

每个受保护请求都验证访问令牌、用户状态和 `token_version`，再检查空间成员关系和资源级权限。客户端提供的 `owner_id` 不得作为授权依据。

### 状态定义

```text
上传记录：created -> uploading -> uploaded -> committed
                                  `-> failed
           created/uploaded -> expired

上传分片：pending -> confirmed
                    `-> failed

逻辑文件：active -> deleted -> active
                         `-> purged

清理记录：created -> running -> completed
                            `-> failed
```

文件版本提交后立即可用，不存在额外的内容处理阶段。

## MinIO 对象规划

建议 Bucket：

| Bucket | 用途 | 生命周期 |
| --- | --- | --- |
| uploads | 未完成上传和临时合并对象 | 上传完成、失败或过期后清理 |
| contents | 不可变正式内容对象 | 仅在无引用且通过物理清理流程时删除 |
| backups | 数据库备份、对象清单和校验文件 | 按备份保留策略管理 |

正式对象键由服务端生成，不使用用户文件名：

```text
Bucket=contents  key={sha256前两位}/{sha256}/{size}/{write_uuid}
Bucket=uploads   key={user_id}/{upload_id}/{随机UUID}
Bucket=backups   key={yyyy}/{mm}/{dd}/{backup_run_id}/{artifact}
```

用户文件名只保存在 PostgreSQL，并在下载时经过安全编码。MinIO Bucket 和 object_key 不直接返回前端。

key不包含Bucket名；随机写入标识隔离迟到写入与删除，ready内容不可覆盖；数据库按SHA-256与大小实现物理去重。

## 核心存储流程

### 批量、分片上传与断点续传

1. 前端可一次选择多个文件，但逐个调用创建上传接口。
2. FastAPI 校验用户、空间、目录、声明大小、类型策略和配额。
3. 大文件创建 MinIO multipart upload；小文件也使用流式写入。
4. 每个分片成功后，后端在 `upload_parts` 中记录 ETag、大小和校验值。
5. 断线重连后，前端读取已确认分片并只上传缺失部分。
6. 完成请求锁定 `uploads` 记录，重复完成请求返回首次提交结果。
7. 后端完成临时对象并重新计算实际大小与 SHA-256。
8. 校验失败时标记失败，不创建可用版本。

### 安全去重与首次版本提交

1. 根据实际 SHA-256 与大小查询 `content_objects`。
2. 已存在相同正式对象时增加引用，不重复写入内容。
3. 不存在时把已校验临时对象复制到新生成的正式对象键，并再次校验；复制和临时删除是独立操作。
4. 在 PostgreSQL 事务中创建逻辑文件、V1 版本、对象引用并更新空间配额。
5. 事务成功后清理临时对象；清理失败记录告警并允许受控重试。
6. 数据库事务失败时保留检查点；零引用正式对象只允许在持有内容协调锁并重新核对实际引用后受控清理，不能直接回滚删除共享内容。

所有新内容必须实际上传并由服务端校验，不提供秒传或全局哈希存在性查询。存储去重只复用内容对象，不复用逻辑文件、所有者、目录、标签或权限。

### 发布新版本

1. 校验操作者是管理员或文件所有者。
2. 完成新内容上传并校验实际大小和哈希。
3. 使用 PostgreSQL 行锁锁定目标 `files` 记录。
4. 计算下一个版本号，并通过唯一约束防止并发重复。
5. 创建不可变版本，更新 `current_version_id`、对象引用和空间配额。
6. 提交成功后立即返回新版本，不执行额外内容处理。

### 历史版本下载与恢复

- 下载历史版本必须执行与当前版本相同的权限校验。
- 恢复历史版本不是移动当前指针，而是创建引用历史内容的新版本。
- 新版本写入 `restored_from_version_id`，完整保留恢复链。
- 版本内容和版本元数据均不得原地修改。

### 元数据搜索

系统只提供一个 `/search` 入口，不接受搜索模式参数。

搜索步骤：

1. 验证账号状态并确定可见空间。
2. 应用文件有效状态和空间权限条件。
3. 应用目录、MIME、扩展名、标签、上传者、日期和自定义元数据过滤。
4. 在文件名、描述、目录名、标签名、上传者名称和文本型自定义元数据中匹配关键词。
5. 按相关度、更新时间或名称排序并分页返回。

名称与描述可使用 PostgreSQL `pg_trgm` GIN 索引支持包含匹配和模糊匹配；结构化过滤字段使用 B-tree 或相应联合索引。关联字段通过受控查询和必要的预聚合实现，不建立独立搜索存储。

每条结果返回 `match_source`、`file_id`、当前 `version_id`、文件位置、MIME、大小、所有者和更新时间。`match_source` 使用 `name`、`description`、`tag`、`directory`、`mime`、`uploader` 或 `custom_metadata` 等受控值。

搜索实现不得读取 MinIO 对象、创建临时文件或尝试识别文件内容。

### 单文件管理、回收站与物理清理

移动、复制、添加标签和移除标签均为单文件接口。每次操作独立鉴权、独立返回并写入审计。

软删除只把 `files.status` 改为 `deleted`，记录 `deleted_at` 和 `deleted_by`。普通列表和搜索立即过滤该文件。恢复会清除删除字段并恢复为有效状态，不改变版本或对象引用。

管理员彻底清理前必须为单个逻辑文件提交一次性二次确认凭据。Service 创建 `cleanup_attempts`，锁定文件并重新检查文件仍在回收站，且所有版本均满足保留策略，然后：

1. 保存清理目标和对象引用快照；在单个短事务内清空当前版本指针、删除标签/自定义值/版本及逻辑文件，扣减引用计数和空间用量，保存detach检查点。
2. 在内容协调锁下重新检查对象ID和键快照；仅当计数与实际版本引用均为零时，删除MinIO对象及内容对象记录；仍被引用的对象保留。
3. 逐项保存对象删除结果，完成清理记录和审计事件。

任一步骤失败都记录失败阶段。重新提交二次确认后按原清理记录重试，已不存在的关联或对象按成功处理，不重复扣减引用和配额。detach已提交后不能从回收站恢复，只能从备份恢复。

| 路径 | 主要职责 |
| --- | --- |
| `/auth` | 登录、刷新、退出、当前用户和会话管理 |
| `/spaces` | 空间、成员和配额管理 |
| `/directories` | 目录树管理 |
| `/upload-batches` | 创建批次并汇总各独立文件上传状态 |

| `/files` | 文件详情、元数据、移动、复制、标签和软删除 |
| `/files/{file_id}/restore` | 从回收站逐项恢复文件 |
| `/files/{file_id}/versions` | 发布、列出和恢复不可变版本 |

修改接口支持 `Idempotency-Key`。稳定业务错误码至少包括 `FORBIDDEN`、`ACCOUNT_FROZEN`、`UPLOAD_EXPIRED`、`PART_MISMATCH`、`HASH_MISMATCH`、`VERSION_CONFLICT`、`RETENTION_BLOCKED`、`LEGAL_HOLD`、`QUOTA_EXCEEDED`、`FILE_NOT_FOUND` 和 `STORAGE_UNAVAILABLE`。

上述分组表示逻辑路径，实际端点统一加`/api`前缀。分片使用分片编号与校验值幂等，认证端点使用会话语义；其他修改端点的幂等要求见接口契约。

## 数据一致性与幂等

### 事务边界

- PostgreSQL 内部更新使用本地事务。
- MinIO 操作不加入 PostgreSQL 事务。
- 跨存储一致性依靠固定执行顺序、状态字段、幂等键、唯一约束和同步补偿。
- 不使用分布式事务、事务事件表或后台补偿任务。

### 幂等策略

| 操作 | 幂等键 | 重复调用结果 |
| --- | --- | --- |
| 创建上传 | 用户编号加 `Idempotency-Key` | 返回同一上传记录 |
| 上传分片 | upload_id 加 part_no | 返回同一 ETag 和确认状态 |
| 完成上传 | upload_id 加 SHA-256 | 不创建重复版本 |
| 发布版本 | file_id 加 `Idempotency-Key` | 返回同一版本结果 |
| 文件复制 | file_id 加 `Idempotency-Key` | 返回同一新逻辑文件 |
| 恢复版本 | file_id、源版本加 `Idempotency-Key` | 返回同一恢复版本 |
| 物理清理 | file_id 加 confirmation_id | 返回同一清理结果 |

数据库唯一约束是最终防线，应用层预检查只用于提供友好错误。幂等响应必须绑定原请求主体摘要，防止相同幂等键被用于不同内容。

## 故障与降级

| 故障 | 影响 | 处理方式 |
| --- | --- | --- |
| PostgreSQL 不可用 | 登录、权限、列表和写操作不可用 | API 就绪检查失败，停止接收业务流量 |
| MinIO 不可用 | 上传、下载和内容清理不可用 | API 就绪检查失败，内容操作返回明确错误，恢复后重新就绪 |
| 临时对象提交后数据库事务失败 | 可能产生孤立对象 | 保存检查点，在内容协调锁及实际引用复查下受控清理 |
| 数据库成功但临时对象清理失败 | 残留临时对象 | 业务结果保持成功，按过期策略受控清理 |
| 客户端上传中断 | 当前文件未完成 | 保留已确认分片，允许断点续传至过期时间 |
| 并发发布版本 | 版本号竞争 | 行锁加唯一约束，冲突请求重试或返回版本冲突 |
| 备份目标不可用 | 当前备份失败 | 记录失败和校验信息，不覆盖最近成功备份 |

任何故障都不得绕过鉴权、配额、保留策略或审计要求。

## 认证与安全设计

- 密码使用 Argon2id 或等价强度算法存储，禁止可逆加密。
- 访问令牌有效期短，刷新令牌只以哈希形式保存于 `refresh_sessions`。
- 退出时立即撤销对应刷新会话；冻结、改密或强制下线时递增 `token_version`。
- 每个受保护请求检查用户状态和 `token_version`，不只依赖令牌签名结果。
- Nginx 对登录、刷新和高频 API 设置按来源地址的基础速率限制；后端仍执行账号级失败审计。
- 数据库密码、JWT 密钥和 MinIO 密钥使用 Docker secrets，不写入镜像或源码。
- 上传同时校验扩展名、声明 MIME、探测 MIME、大小、配额和服务端允许策略。
- 下载设置 `X-Content-Type-Options: nosniff`，危险格式默认以附件方式下载。
- 日志不得记录密码、完整令牌、密钥、文件内容或敏感自定义元数据。
- 管理接口不接受任意 SQL、对象路径或宿主机命令。
- 所有资源编号使用不可预测标识，但仍必须执行资源级鉴权。

## 单机部署与运行

### 生产服务器目录

```text
/srv/file-manager/
  compose.yaml
  compose.prod.yaml
  .env
  configs/
    nginx/
    prometheus/
    grafana/
  secrets/
  data/
    postgres/
    minio/
    prometheus/
    grafana/
  backups/
  logs/
```

`compose.yaml` 定义 nginx、api、postgres 和 minio 服务。API 使用由 `backend/` 源码构建的固定版本镜像；生产服务器不绑定挂载应用源码。

数据目录挂载独立数据盘。`secrets` 文件权限设置为 600，目录只允许运维账号访问。

### 健康检查

| 服务 | 存活检查 | 就绪检查 |
| --- | --- | --- |
| API | `/api/health/live` | PostgreSQL 与 MinIO 可用，迁移已完成 |
| PostgreSQL | `pg_isready` | 应用账号可执行只读探针 |
| MinIO | live | ready 且必要 Bucket 存在 |
| Nginx | 本地 HTTP 探针 | 静态页面和 API 反向代理可达 |

`/api/health/live` 只表示进程存活；`/api/health/ready` 决定是否接收业务流量；`/api/admin/components` 向管理员展示更详细但经过脱敏的状态。

### 备份与恢复

| 数据 | 备份方式 | 建议频率 | 说明 |
| --- | --- | --- | --- |
| PostgreSQL | `pg_dump` 自定义格式 | 每日 | 保存全部业务元数据和审计 |
| MinIO | 对象增量复制加周期清单 | 持续或每日 | 恢复后按 SHA-256 抽样或全量校验 |
| 配置与密钥 | 加密备份 | 每次变更后 | 与业务备份分开保管 |

备份命令先生成清单、大小、SHA-256、开始与结束时间和结果状态，再上传到异地 S3 兼容存储。备份执行不依赖常驻任务容器。

恢复顺序：

1. 恢复 Compose、配置和密钥。
2. 恢复 MinIO 文件对象并校验样本哈希。
3. 恢复 PostgreSQL。
4. 启动 API 和 Nginx。
5. 核对 PostgreSQL 引用的 MinIO 对象是否存在，并识别孤立对象。
6. 完成登录、上传、下载、版本发布和搜索冒烟测试。

每季度至少执行一次隔离环境恢复演练，并记录恢复时间、数据缺口和修正措施。

## 可观测性

核心日志包括 Nginx 访问日志、API 业务日志、认证与安全日志、存储操作日志、备份日志和 PostgreSQL 审计事件。

重点指标包括：

- API 请求量、响应时间、错误率和并发数。
- 登录失败、令牌刷新失败、权限拒绝和入口限流次数。
- 上传吞吐、分片失败率、完成上传耗时和过期上传数量。
- 下载吞吐、首字节时间和中断数量。
- PostgreSQL 连接池、慢查询、事务冲突、行锁等待和容量。
- MinIO Bucket 容量、对象数、未完成上传和错误率。
- PostgreSQL 与 MinIO 引用不一致数量和孤立对象数量。
- 备份成功率、备份大小、校验结果和最近恢复演练时间。

日志和指标使用 request_id、user_id、file_id、upload_id 和 backup_run_id 关联，但不得使用文件内容作为标签。

## 性能与容量边界

- 上传和下载全程流式处理。
- 大于 5 MB 的文件使用分片上传，单分片建议 8 至 32 MB。
- 一次批量选择至少支持 100 个文件，每个文件独立显示状态和重试入口。
- 前端上传并发默认不超过 4，可由受控配置调整。
- API 不在内存中保留完整文件，只保留当前流式缓冲区。
- 文件列表和搜索必须分页，默认页大小不超过 50，最大不超过 200。
- 高频过滤字段建立适当数据库索引；搜索慢查询必须进入监控。
- 容量规划分别统计 PostgreSQL 元数据增长、MinIO 逻辑版本大小、物理对象大小和去重率。
- 临时上传对象按过期时间清理，清理前必须确认对应上传未处于活动状态。

## 验收标准

1. 核心 Compose 只包含 nginx、api、postgres 和 minio，不包含常驻任务服务或消息队列。
2. PostgreSQL 保存全部业务元数据、权限、会话、上传进度、审计和备份记录。
3. MinIO 只保存临时上传对象、不可变内容对象和备份包，不承担权限判断。
4. 所有文件使用同一数据模型和同一上传流程，数据模型中不存在文件内容处理状态。
5. 系统不提取、保存或搜索文件正文，搜索请求不会读取 MinIO 对象。
6. `/search` 不接受搜索模式参数，只搜索受控元数据字段并支持组合筛选。
7. 前端不存在文档专属分类、内容处理状态或相关重试入口。
8. 账号密码登录签发短期访问令牌和可撤销刷新令牌，退出后刷新令牌立即失效。
9. 冻结、改密或强制下线后，已有访问令牌因用户状态或 `token_version` 检查而失效。
10. 使用者不能通过替换文件、版本、上传或对象编号操作其他人的文件。
11. 一次选择 100 个文件时前端保持响应，每个文件独立上传，失败不回滚其他文件。
12. 网络中断后只补传缺失分片，重复提交分片不会生成重复记录。
13. 完成上传重新校验大小和 SHA-256，校验失败不得形成文件版本。
14. 重复完成同一上传只返回首次结果，不创建重复文件或版本。
15. 所有新内容实际上传并经服务端校验；存储去重不合并逻辑文件、归属、目录或权限，不提供秒传。
16. 首次上传生成 V1；并发发布不得产生重复版本号或错误的当前版本指针。
17. 历史版本不可修改，恢复历史版本会创建新版本并保留来源关系。
18. 当前和历史版本均由 FastAPI 鉴权并流式转发，浏览器不直接访问 MinIO。
19. 元数据搜索支持空间、目录、MIME、扩展名、标签、上传者、日期、状态和自定义元数据组合筛选。
20. 搜索结果返回受控匹配来源，并在返回前应用账号、空间、文件状态和权限条件。
21. 软删除后文件只在回收站可见；管理员可逐项恢复，使用者只能恢复本人文件。
22. 彻底清理跳过仍在保留期或处于合规冻结状态的版本。
23. 管理员使用一次性二次确认凭据同步彻底清理单个文件；失败阶段可记录并幂等重试。
24. 删除一个内容引用不会删除仍被其他版本引用的 MinIO 对象。
25. 文件移动、复制、标签、删除、恢复、版本发布和下载均逐项鉴权并写入审计。
26. PostgreSQL 与 MinIO 不向公网暴露端口，生产服务器不绑定挂载应用源码。
27. PostgreSQL 和 MinIO 任一不可用时，API 就绪状态准确反映依赖故障。
28. 备份包含数据库、对象清单、配置和密钥，并能在隔离环境完成恢复演练。
29. 架构图、数据模型、接口、源码结构、部署目录、健康检查和备份方案使用一致的组件边界。

## 实施约束

- 当前为新系统架构基线，不提供旧数据模型或旧接口的兼容层。
- 数据库迁移从本文档定义的最小模型开始，不创建已删除能力的占位字段或空表。
- 后续新增文件内容处理能力时，必须单独进行架构评审，不得直接扩展核心上传事务。
- 后续新增外部组件时，必须说明权威数据边界、故障影响、备份恢复和权限校验方式。
